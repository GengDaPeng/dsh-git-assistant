## (c) Install / upgrade path, "live" criteria, approval, rebuild, serving

- **Install**: `plugin_manager` `action: install_bundle` with an absolute package directory (`SKILL` skill body; `SKILL/references/host-plugin.md:81`). It runs the profile's package manager (`pnpm add <spec>`; registry targets `--save-exact`, local/development targets `link:<abs dir>` — `ASAR/dsh-plugin-manager/lib/index.js:2801-2806`, `ASAR/dsh-plugin-manager/README.md:52,54`), writes the dependency into the profile `package.json` (e.g. `dsh-agent-message` is `link:/Users/gpp/project/github/dsh-msg` — `$DSH_PROFILE_DIR/package.json:6`), appends the bundle to `dsh.profile.bundles` (`:26-33`; "Installation enables a new bundle by default" — `ASAR/dsh-plugin-manager/README.md:40`), validates the bundle patch, then activates. A bundle toggle only edits `dsh.profile.bundles`; a row toggle writes `disabled` into the profile `cordis.patch.yml` (`ASAR/dsh-plugin-manager/README.md:40,83-85`; live patch rows at `$DSH_PROFILE_DIR/cordis.patch.yml:4-55`). `cordis.yml` stays an empty root list (`$DSH_PROFILE_DIR/cordis.yml:1-4`).
- **Acceptance / "live"**: read the result's `application` + `warnings`, not logs: `applied` (live), `restart-required` (with `reason`: `no-hmr`/`package-moved`), `failed`, `overridden`, `cancelled` (`ASAR/dsh-plugin-manager/lib/types/tools.js` enums; `ASAR/dsh-plugin-manager/README.md:126,130,155`; `SKILL/references/host-plugin.md:83`). Confirm with approval-free inspection afterwards, not `list_plugins` (`SKILL` skill body step 4). This profile enables HMR: the `@deepseek-ai/dsh-web-app` bundle patch inserts `client-hmr` and `modules` rows (`ASAR/dsh-web-app/cordis.patch.yml:214-228`), and the profile does not override them. So a **new** bundle activates live; **replacing** an installed package needs a restart for a fresh JS generation (`SKILL/references/host-plugin.md:83`; `ASAR/dsh-plugin-manager/README.md:126`).
- **Approval implications**: every `plugin_manager` action (even `list_plugins`) requires `danger-full-access` or an approval for that call; under lower sandbox modes `ask` prompts, and rejection/cancellation blocks execution (`ASAR/dsh-plugin-manager/README.md:31`). Profile changes persist across sessions, and **installed Host code executes in-process outside the workspace sandbox**; dependency build-script approval is separate (`approvedBuilds`) (`:31,72`; `SKILL/references/host-plugin.md:81`). This session has approval prompts disabled, so I made no `plugin_manager` call.
- **Does the Desktop app / `app.asar` need rebuilding? NO.** Plugins live entirely in the profile: dependencies in `$DSH_PROFILE_DIR/package.json`, rows in the profile patch layers, client artifacts in `$DSH_PROFILE_DIR/node_modules/<pkg>`; the Host reads each package manifest when its Loader entry starts (`ASAR/dsh-client-modules/README.md:149`) and serves `/plugins/*` from disk at runtime. The asar contains only the DSH installation (`dsh/node_modules/@deepseek-ai/*`); no third-party plugin is baked into it. Desktop-specific evidence it serves profile plugins at runtime: "Desktop re-reads package assets on every display — the Desktop forwarder rewrites every `/plugins/` cache header to `no-store`" (`ASAR/dsh-client-modules/README.md:150`). So a new sidebar plugin needs no Electron/asar rebuild; at most a page reload or DSH restart for replacement code.
- **How client code is bundled/served**: host-side registry snapshots each package's `client.js`, groups rows into `/plugins/??…&rev=…` combos (each phase split before the URL exceeds 3 KiB; `ASAR/dsh-client-modules/README.md:81-85`), and serves whole prebuilt files (no per-request bundling). Package assets use `/plugins/<package>/assets/<path>` resolved through the package's `"./assets/*"` export, filenames stamped with a 12-hex SHA-1 content revision, `cache-control: public, max-age=31536000, immutable`, extensions limited to `.svg/.png/.webp/.jpg/.jpeg` (`:39`). There is **no documented code-size cap**; observed shipping client bundles: 245 KB (`dsh-media-desk`), 262 KB (`dsh-cost-meter`), 438 KB (shipped `ui-plugin-manager`), 916 KB (`dsh-context`).

## (e) Hard limits

- **Trust/sandbox**: Host plugin code runs in-process, outside the workspace sandbox, after an approval-gated install; client bundle code runs in the Web UI origin with full DOM/window privileges (`ASAR/dsh-plugin-manager/README.md:31`). No app-document CSP was found in the installed serving code (scan of shipped JS for `content-security-policy`); the only CSPs found are on served artifacts (SVG assets `content-security-policy: script-src 'none'`, `ASAR/dsh-client-modules/lib/index.js` package-asset route; media route `sandbox; default-src 'none'`, `ASAR/dsh-api-session-controller/lib/index.js`; sanitized document-preview iframe policy, `ASAR/dsh-client-ui-sidebar-documentpreview/lib/client.js`).
- **Module loading**: only the shell's frozen platform table plus rows' declared `dsh.client.external`; composition rejects malformed requests, missing suppliers, self-requests, and synchronous cycles (`ASAR/dsh-client-modules/README.md:55`). Do **not** `require('@deepseek-ai/dsh-client-ui-primitives')` or any other Harness Client package; `inject` entries only order activation (`SKILL/references/practices.md:35`). A throwing component blanks its slot entry.
- **Pages are React-in-slot, not iframes**: "Render plugin pages as React components in a slot. Do not serve an HTML page from the Host and embed it in an iframe: an iframe document does not receive the host's theme tokens, light/dark switching, or `ctx.locale`" (`SKILL/references/practices.md:33`). `dsh-guizang-design` deliberately deviates with a same-origin iframe plus `postMessage` theme/locale bridging (`PROFILE/dsh-guizang-design/lib/client.js:26-68`) — workable but not the recommended path. Never replace the app root or append a second app to `document.body` (`SKILL/references/ui-plugin.md:13`).
- **Styling**: only `--dsw-alias-*` theme tokens for the host look, literal colors for artwork only (`SKILL/references/practices.md:34`); copy host markup/behavior rather than importing primitives.
- **Version/platform gates**: `dsh.bundle.platforms` restricts OS (`ASAR/dsh-package-manifest/README.md:55`); `engines.dsh` is enforced (see (g)); DSH release identity gates which graph a page applies (`ASAR/dsh-client-modules/README.md:51`).
- **HMR/dev**: `pnpm run dev:web` starts Host + rebuild watchers; rebuilt bundles hot-swap with fresh React state (`ASAR/dsh-client-hmr/README.md:32-48`). Linked local packages still need "rebuilding and restarting … after code changes" (`ASAR/dsh-plugin-manager/README.md:52`); replacement code needs restart (`SKILL/references/host-plugin.md:83`). After HMR, "remember: React state inside the reloaded plugin is lost" (`ASAR/dsh-client-hmr/README.md:48`).
- **Asset**: icon ≤256 KiB (d); package assets only via the `./assets/*` export and the five image extensions (c).

## (g) Lead follow-ups

**1) `engines.dsh` gate: enforced (not a warning), but prereleases are explicitly included — upstream `^0.2.1-alpha.2` PASSES on 0.2.2-rc.1.**
- Runtime version = app-boot package version: `ASAR/dsh-app-boot/lib/index.js:1089-1093`; it is `0.2.2-rc.1`.
- `function satisfies(runtimeVersion, range) { return range.trim() !== "" && semver.satisfies(runtimeVersion, range, { includePrerelease: true }); }` — `ASAR/dsh-app-boot/lib/index.js:1094-1096`. **`includePrerelease: true` is the decisive detail.**
- Own `engines.dsh` decides alone; `peerDependencies` are ignored when it exists (`:1097-1104`, doc `:1118-1122`). So the upstream's `^0.2.1-alpha.2` peer ranges (incl. `@deepseek-ai/dsh-client-ui-slots`, which no longer exists as a package in 0.2.2-rc.1 — its `package.json` path in the asar is absent) do not participate.
- Install preflight **blocks**: `evaluatePluginCompatibility(manifest, exemptions)`; an unmet, non-exempt issue is pushed and the operation returns `rejected(..., "nothing was installed")` before pnpm runs (`ASAR/dsh-plugin-manager/lib/index.js:697-701`; for a local path the manifest is read directly from `package.json` — `:500-503`). Post-install re-check: `:2843-2844` (`ManagementFailure("incompatible-version")`; a registry run can also classify `incompatible-version` at `:2809`).
- Activation **denies**: bundle layer load throws `pluginCompatibilityWarning(issue)` and the bundle is skipped at boot (`ASAR/dsh-app-boot/lib/index.js:1800-1822`); at row preflight "Only a compatibility conflict denies a row" → `row.disabled = true` (`:3109-3120`).
- Empirical check with the profile's own semver (Node v24.21.0, `semver` 7.8.6 from `$DSH_PROFILE_DIR/node_modules`): `satisfies('0.2.2-rc.1','^0.2.1-alpha.2',{includePrerelease:true}) === true` (and `false` without `includePrerelease`). So the gate is satisfied for this runtime; **no patched copy is required on the engines axis** and no `compatibility.json` version exemption is needed. An exemption would only be needed if a future host stops matching (mechanism: profile `compatibility.json`, exact `name@version` → exact runtime versions; `ASAR/dsh-plugin-manager/README.md:79`).
- Caveat: the upstream manifest also declares `dsh.manifestVersion: 1`, which nothing enforces ("Current installers and loaders do not enforce `dsh.manifestVersion` or `engines.dsh`" refers to the *type package's* own readers — `ASAR/dsh-package-manifest/README.md:96` — while app-boot does enforce `engines.dsh` for bundles/rows as cited above).

**3) Does `install_bundle` build a local directory? NO — it never runs the package's build.** The install path only calls `pnpm add` with the spec (`ASAR/dsh-plugin-manager/lib/index.js:2801-2806`); there is no `pnpm run build`, `prepack`, or `prepare` invocation in the manager. Consequences:
- A **hand-authored plain-JS** bundle (the skill template, or a copy of a built dist) needs no build step at all — `client.js`/`index.js` are authored files.
- A **TypeScript/source checkout** such as `research/upstream/dsh-superagent-prototype` (has `src/`, `tsdown.config.ts`, `main: lib/index.js`, no `lib/`) must be built by its author **before** install: "Missing packages, bundle patches, or built entry points produce a diagnostic without registry fallback. Prepare the checkout with `pnpm install` and `pnpm run build`" (`ASAR/dsh-plugin-manager/README.md:52`); for official dev link targets the manager explicitly checks `main` exists and throws "built runtime is missing … run pnpm install and pnpm run build" (`ASAR/dsh-plugin-manager/lib/index.js:1037`). For an arbitrary local dir, a missing `main`/`client.js` surfaces as an activation `failed` (import error), not a build.
