- Package: `dsh-superagent@0.1.0`, `private: true`, MIT, `engines.dsh ^0.2.1-alpha.2`, Node `^22.19.0 || >=24.0.0` (`package.json:2-6,53-56`).

- Citation convention: `path:line` is relative to the clone root. **[impl]** = code in this repo; **[doc]** = documented designed behaviour; **[future]** = docs say not implemented; **[env]** = this machine's packaged DSH; **[probe]** = concurrent team build probe at `research/build-probe/` (`logs/exp1-*.log`, `logs/exp2-*.log`; not upstream evidence).

## 1. What the project actually is

- **[impl]** A proactive coding agent for **one GitHub repository**, packaged as a DSH bundle: it listens to GitHub and optionally Feishu, opens a work item for authorized requests, executes each in its own DSH Session and directory, and answers in the original conversation; a web panel shows what needs a person (`README.md:7`).
- **[future]** It is explicitly adapted for publication and "not identical to our internal version or the implementation described in the article"; some designs in the article are future directions not implemented here (`README.md:5`).
- **Core principle:** take as little human attention as possible, give as much value as possible; act only when asked or when a written rule allows it; speak only when a person must act (`docs/000-philosophy.md:3-16`).
- **Domain model [doc]:** `Source → Trigger → Thread → Eval → Ticket → Assignment → Executor`, with `Policy/Mandate/Subscription/Channel/Correlation`; only a Source's Trigger enters the system, a Thread owns at most one running Eval, a Ticket is authorized work holding a Mandate (`docs/001-domain.md:7-19,27-37`). The Executor (DSH Sessions + directories) is outside the domain and connects via Assignments (`docs/001-domain.md:41`).
- **Identities:** always Source-native and never mapped across Sources; an allowed list is a Source's part of the Policy (`docs/001-domain.md:39`, `docs/002-authorization.md:56-75`).
- **Authorization [doc]:** deterministic "gate" in front of every Trigger — allowed sender addressing the agent = explicit request; unlisted senders / unaddressed messages / bots use the admission table and become inferred candidates only; accept modes `off` / `observe` (default, records "would accept") / `auto` (`docs/002-authorization.md:9-17,46-54,91-101`). Only accept creates, a human stop withdraws, failed revalidation revokes a Mandate (`docs/002-authorization.md:125-141`).
- **Execution model [impl/doc]:** each Ticket gets an Executor Session named `worker-<ticket id>` (`src/executor/dsh.ts:24`) plus a directory; before the first Assignment a configured `prepare` command may create a git worktree; one worker slot per running Ticket plus one extra slot for human input; each turn's background jobs/subagents may run up to 30 minutes (`docs/003-execution.md:23-61`; `src/executor/dsh.ts:32`; `src/executor/background.ts:1-5`).
- **Prompts [impl]:** three team-editable sections (Communication, Ticket scope, Delivery requirements) plus team skills; built-in prompt parts and skills are overrideable with versioning (`docs/004-prompts.md:5-34,44-56,91-96`; `src/app/prompts.ts:46-114`).
- **Panel [doc]:** sidebar "Superagent" opens a supervision panel with tabs Overview / Source / Trigger / Eval / Execution / Settings; it prioritises work that needs a person, then health and history (`docs/005-panel.md:3,13-24,34-42`).
- **Deployment [doc]:** a dedicated DSH profile (called `superagent`), a dedicated agent GitHub account acting through its own `gh` wrapper, optional Feishu bot through `lark-cli`, a repository clone used for per-Ticket checkouts, and a model provider already configured in DSH (`docs/006-deployment.md:5-11,21-69`).

## 2. Bundle shape

- **Manifest [impl]:** `main`/`types` → `lib/index.js`/`.d.ts`; subpath exports `.`, `./client`, `./github-watch`, `./feishu-watch`, `./locale/*.json` (`package.json:9-21`); `files` ships `lib`, `cordis.patch.yml`, `locale`, `prompts`, `skills` (`package.json:22-29`).
- **Bundle declaration [impl]:** `dsh.bundle.patch = ./cordis.patch.yml` (`package.json:30-33`), plus `dsh.client = { platform: "web", inject: [locale, ui-settings, ui-renderer, ui-layout, ui-sidebar, ui-workspace] }` (`package.json:34-46`) — a standard DSH bundle with a Host module and a Web client module.
- **Patch rows [impl]:** one `insert` list adds three plugins — `dsh-superagent` (package root), `dsh-superagent/github-watch`, `dsh-superagent/feishu-watch` (`disabled: true`) — followed by two `@deepseek-ai/dsh-agent-preset` rows that define agent presets `dsh-superagent-worker` (order 90) and `dsh-superagent-router` (order 91) (`cordis.patch.yml:4-12,20-193`).
- **Presets [impl]:** the worker preset is `standard` minus ask/present/plan/plugin-manager/market/schedule/goal/workflow/web-fetch/forked-subagents, plus a 5 s shell and 5 s job-wait limit (`cordis.patch.yml:20-120`); the router preset is smaller (no subagents, web, fs-search, writes, todo, human questions) (`cordis.patch.yml:125-193`).
- **Profile layer [impl]:** the host row needs `config.stateDir` (absolute; database, lock, worker shims, agent git config, default Ticket root); `webserver` sets host/port; the Feishu row is `disabled: true` in the bundle and enabled by the profile layer (`examples/profile.cordis.patch.yml:3-12`; `src/deployment.ts:14-22`; `cordis.patch.yml:9-12`).
- **Host side [impl]:** ESM entries `index`, `github-watch`, `feishu-watch` platform node (`tsdown.config.ts:10`); client is a browser CJS artifact registered through `window.__ModuleLoader__.load({ id: "dsh-superagent", ... })` (`tsdown.config.ts:11-13`).
- **DSH services required [impl]:** `agents, sessionController, sessionPersistence, workspaceRegistry, permissionPresets, tools, systemPrompt, skills, webServer, llm, subprocess` (`src/index.ts:8`), with `settings` optional (`src/index.ts:13`); it also uses DSH's `jobs` and `subagents` services when present (`src/executor/background.ts:1-5,29-30`).
- **Internal service [impl]:** `Runtime` provides the `orchestrator` Cordis service (`src/app/runtime.ts:51,59`); GitHub/Feishu Source plugins declare `inject = ['orchestrator']` (`src/sources/github.ts:110-112`, `src/sources/feishu.ts:130-132`).
- **External dependencies [doc]:** GitHub CLI (`gh` wrapper signed in as the agent account), optional `lark-cli` bot-only config, git 2.32+, tmux, Python 3.8+; GitHub Enterprise not supported; Feishu optional (`docs/006-deployment.md:21-27`). There is no GitHub/Feishu SDK dependency — all I/O goes through those CLIs (`package.json:58-61` only runtime deps are `proper-lockfile`, `zod`; `src/infra/commands.ts` is the transport).
- **Peer dependencies [impl]:** 23 `@deepseek-ai/*` packages pinned `^0.2.1-alpha.2` (and `@deepseek-ai/cordis 4.0.5-alpha.1`) (`package.json:62-86`).
- **Storage [impl]:** single SQLite database `<stateDir>/orchestrator.sqlite`, opened under a `proper-lockfile` lock on the state dir (`src/app/runtime.ts:91-98`); tables for trigger, disposition, thread, ticket, decision, effect, outbox, kv (`docs/007-architecture.md:450-464`).

## 3. Interaction surfaces it exposes

- **No chat UI of its own [impl].** The client registers exactly three slots: a `main` panel `dsh-superagent`, a `sidebar.panellist` entry `dsh-superagent` (order 10, label "Superagent"), and a `plugins.row.config` form for the Plugin Manager (`src/client/index.tsx:53-57`; asserted in `tests/client.spec.tsx:52-59`). Panel pages are Overview/Source/Trigger/Eval/Execution/Settings — admin views only, no conversation, message list or composer (`src/client/route.ts:6-8`; `docs/005-panel.md:13-24`).
- **Chat belongs to the DSH host.** The only chat-like paths are two navigation buttons: "Open main Session" in the panel header (`src/client/app.tsx:101,134-135`) and per-Ticket "Open Session" buttons for worker Sessions (`src/client/widgets.tsx:91-95`; `src/client/ticket.tsx:64-65,134`). Both call DSH's `uiWorkspace.openSession` after verifying the Session is in DSH's catalog (`src/client/index.tsx:34-43`; `src/navigation.ts:14-22`). The bundle neither injects nor depends on DSH's chat client packages (`package.json:36-43,62-86`).
- **How a human starts work [doc]:** (a) GitHub — from an allowed account comment `@<agent login> <request>` on an Issue; the agent account's notifications are polled (60 s default) (`docs/006-deployment.md:229-231`; `src/sources/github.ts:25,144`); (b) Feishu — mention the bot in a configured chat (bot reads mentions, optional all-message mode / DMs) (`SETUP.md:37,59`; `docs/006-deployment.md:147,202`; Feishu row disabled by default `cordis.patch.yml:9-12`).
- **Panel actions (human ops, not chat) [impl]:** retry/stop Ticket, pause/resume processing, unsubscribe a Thread, re-evaluate a Trigger, dismiss an unavailable Decision, re-run setup, edit Sources/Policy/Eval/Execution/Prompts and history (`src/app/api.ts:21-45`; `docs/006-deployment.md:169-205`).
- **Management HTTP API [impl]:** loopback-only, same-origin + `x-orchestrator-request: 1` guard under `/orchestrator/api/` (`src/app/http.ts:75-78,230-245`; `docs/006-deployment.md:159-167`); it is the panel's transport and is usable by agents/scripts. Its typed route list contains **no route to send a chat message or create work from free text** (`src/app/api.ts:21-45`).
- **DSH Session interplay [impl]:** the plugin creates and decorates a main Session (`masterId = orchestrator-<sha256(stateDir)[0:32]>`, persisted in KV) and one `worker-<ticketId>` Session per Ticket, both with its own agent presets and `danger-full-access` (`src/app/runtime.ts:104-105,210`; `src/app/sessions.ts:138-154`). It delivers work only internally: relays/notices are steered or injected into the main Session (`src/app/sessions.ts:104-105,161-186`). A worker Session also accepts a person typing directly into it and starts a turn from that (`docs/003-execution.md:41`; `src/executor/dsh.ts:223-224,488-491`).
- **Operational surfaces [doc]:** `scripts/dsh-superagent start|status|restart|stop` (tmux, exit codes 0/1/2/3) (`docs/006-deployment.md:101-131`) and an hourly health check prompt for the operator's normal profile (`docs/006-deployment.md:133-141`).

## 4. How it installs into a DSH profile (and the packaged Desktop app)

- **Repo-prescribed install [doc]:** `npm install -g @deepseek-ai/dsh@0.2.1-rc.3`; clone; `pnpm install && pnpm build`; `dsh superagent --from-default-profile web --dump-config > /dev/null` (creates `~/.dsh/profiles/superagent` from the Web template); `dsh plugin --profile superagent add "link:$PWD"` (`docs/006-deployment.md:73-85`). The build is mandatory because the manifest points at `lib/` (`package.json:9-15`; `tsdown.config.ts:9-13`).
- **Machine config [doc]:** copy `examples/profile.cordis.patch.yml` over the profile's `cordis.patch.yml`, fill absolute `stateDir`, set `webserver.port` (example 3082), optionally enable `dsh-superagent-feishu` (`docs/006-deployment.md:89-98`; `examples/profile.cordis.patch.yml:1-12`). The plugin **refuses to start without `stateDir`** (`cordis.patch.yml:1-3`; required schema field `src/deployment.ts:15-17`).
- **Secrets/config [doc]:** agent GitHub account + its own `gh` wrapper (`GH_CONFIG_DIR` isolated) signed in; repository with push access; optional Feishu self-built app + bot-only `lark-cli` config; DSH model provider configured (profile default model unless Eval/Execution sets another); no secret is asked in chat — operator runs those commands (`docs/006-deployment.md:31-69`; `SETUP.md:11-13,27`).
- **DSH features required [impl]:** a Web-app profile supplying the 11 injected services above; a loopback Web server (`src/app/http.ts:231` requires `webServer.host === '127.0.0.1'`); the subprocess service for setup probes and worker shells (`src/app/setup.ts:74,93`); DSH settings service for Plugin Manager config forms (optional) (`src/index.ts:12-20`; `docs/007-architecture.md:604-608`); agent-preset registry for the two presets (`docs/006-deployment.md:244-246`). Worker subagent/job services are optional (`src/executor/background.ts:1-5`). No `forge` plugin is referenced anywhere in `src/`, `package.json` or `cordis.patch.yml` (repo grep), and the presets deliberately omit workflow/goal/schedule rows (`cordis.patch.yml:13-19`); SETUP builds the profile from the shipped `web` template (`docs/006-deployment.md:79`).
- **Packaged Desktop observations [env]:** the installed app is `DeepSeek Harness.app` with an Electron host and a bundled CLI at `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh` reporting `0.2.2-rc.1`; `dsh` is **not on PATH** in a login shell; `~/.dsh/profiles/{desktop,web,…}` exist and the `desktop` profile patch already enables `@deepseek-ai/dsh-client-ui-chat` and `@deepseek-ai/dsh-client-ui-conversation` (`~/.dsh/profiles/desktop/cordis.patch.yml:20-21,35-36`), i.e. the packaged app's profile loads DSH's chat client plugins.
- **Version mismatch risk [env/probe]:** repo engines `^0.2.1-alpha.2` (`package.json:53-56`) and SETUP pins `0.2.1-rc.3` (`docs/006-deployment.md:76`); locally `semver.satisfies('0.2.2-rc.1','^0.2.1-alpha.2') === false`. **[probe]** with deps pinned to `0.2.1-alpha.2` the checkout installs, typechecks and builds cleanly; with deps bumped to the Desktop app's `0.2.2-rc.1` install succeeds but `tsc --noEmit` reports 8 API-drift errors (e.g. missing `SessionController.inspect`, `ConfigFormSnapshot.mode`, renamed `ModelSelectionRef`; see `research/build-probe/logs/exp2-typecheck.log`, clean baseline `exp1-typecheck.log`/`exp1-build.log`). So the prototype as published targets DSH 0.2.1; running it under the packaged Desktop's 0.2.2 needs a port/fix pass at minimum.
- **Install path divergence [env]:** in this environment the supported way to add a bundle to the running profile is DSH's Plugin Manager `install_bundle`, which performs package installation and bundle selection and warns against reproducing it with shell commands (`…/app.asar/dsh/node_modules/@deepseek-ai/dsh-agent-preset/skills/cordis-plugin-development/references/host-plugin.md:79-83`); the repo instead instructs a CLI `dsh plugin … add` plus hand-copying a `cordis.patch.yml` machine layer (`docs/006-deployment.md:73-98`). The dedicated-profile design (separate process, own port 3082, tmux service, hourly repair check) is deliberate because the plugin changes process-wide `PATH`/git config and needs independent restarts (`docs/006-deployment.md:5-19,224-226`; `src/infra/environment.ts:118-120`).
- **Assessment for the packaged Desktop app [judgement from the evidence above]:** the bundle format and client slot mechanism are standard DSH, so installing it into a Desktop profile is *mechanically conceivable*, but the repo documents and tests only a separately booted Web profile. The practical blockers are the DSH 0.2.2-vs-0.2.1 drift, `stateDir` being required before the row can mount, the plugin's process-wide environment changes in the user's main profile, and the full GitHub-account setup gate. Running it as documented (its own `superagent` profile and port) would put the sidebar entry in that profile's Web UI, not in the user's normal Desktop sessions UI.

## 5. What is missing for a sidebar entry that opens a chat with the superagent

What exists today: a sidebar entry that opens the **admin panel** (`src/client/index.tsx:53-55`), and one click inside it opens the main Session's DSH chat (`src/client/app.tsx:134-135`). The main Session is a normal DSH Session, visible in DSH's session catalog and openable through `uiWorkspace.openSession` (`src/app/sessions.ts:138-154`; `src/navigation.ts:13-22`). So the *navigation* plumbing is essentially present; the gaps are product-surface and authorization. None of `docs/000`–`008` mentions a chat UI or a DSH-chat Source: the UI is defined as a supervision panel (`docs/005-panel.md:3,13-24`), so a chat surface is absent rather than "documented future work".

1. **No chat page in the bundle.** The client registers one `main` panel whose pages are all admin views (`src/client/index.tsx:53-54`; `src/client/route.ts:6-8`); no conversation component, composer, message list or streaming handler exists anywhere in `src/client/`. The bundle's peer deps/client injection list excludes DSH's chat packages (`package.json:36-43,62-86`), so a chat page would either embed `@deepseek-ai/dsh-client-ui-chat`/`ui-conversation` (configured in the Desktop profile **[env]**) or re-implement a chat.
2. **No "chat → authorized work" path.** Authorization is Trigger-based: only a Source emits a Trigger, the gate checks sender identity/policy, and Eval/route act on `trigger_id`s (`docs/001-domain.md:7,27-37`; `docs/002-authorization.md:9-17`; `src/core/intake.ts:17-30`; main routing tool takes `trigger_id`, `src/app/tools/main.ts:44-47,122-130`). There is no Source kind for DSH chat, no HTTP route to submit a message (`src/app/api.ts:21-45`), and no main-Session tool that creates a Trigger/Ticket from a human chat message. A "chat with the superagent that actually does work" needs a new Source (or equivalent authorization path) for this surface; `docs/008-cookbook.md:5-11,413-424` is the extension recipe.
3. **Main Session is a router, not a chat partner.** Its system prompt is a complete replacement (no DSH coding prompt) instructing it to assess/route candidates, never investigate, and never wait — candidate cards/reports arrive by themselves (`src/app/sessions.ts:244-249`; `prompts/orchestrator.md:1-16`; `prompts/shared.md:1-7`; `prompts/dispatch.md:1-6`). Its tool set is restricted to `skill, bash, read, read_image, job_output, job_list, job_kill` plus 14 `orchestrator_*` application tools (`src/app/sessions.ts:262-264`; `docs/007-architecture.md:490-501`; `src/app/tools/main.ts:122-301`); none asks a person or creates work from text. Human chat messages are therefore out-of-design: at best the model answers conversationally, but nothing reaches the Trigger/Ticket pipeline.
4. **Session identity/lifecycle must be reused, not re-created.** The managed main Session id is derived/persisted (`masterId`, `src/app/runtime.ts:104-105`), created only after setup succeeds (`src/app/runtime.ts:201-211`), and its role preset is forcibly restored if DSH selects another before the first turn (`src/app/sessions.ts:124-132,142-146`). A chat page must bind to that Session (or extend `Sessions.ensure`); opening/creating any other Session would show a Session with no orchestrator prompt, tools or state.
5. **Setup gate blocks any chat until a full deployment exists.** On a fresh install the plugin registers HTTP routes but returns before creating the main Session unless the GitHub repository + agent CLI + environment check pass (`src/app/runtime.ts:201-211`). Until then "Open main Session" fails with a localized "session not listed" error (`src/navigation.ts:19-21`; `tests/client.spec.tsx:71-78`). Unlike a standalone chat plugin, this bundle is unusable conversationally until a GitHub account/repo, `gh` wrapper, stateDir and model provider are configured — that is the largest gap between "install a plugin" and "chat with the superagent".
6. **Identity/authorization semantics for a chat actor are undefined.** Policy checks operate on Source-native identities (GitHub login / Feishu open_id) and never map across Sources (`docs/001-domain.md:39`; `docs/002-authorization.md:56-75`). "Who is the human in a DSH chat, and on which allowed list?" has no answer in the code or docs; a chat Source would have to define an actor id, an admission row and setup facts.
7. **UI polish/dependency gap.** The panel deliberately uses local copies of DSH controls and a hand-written CSS kit because it does not depend on DSH's UI primitives (`docs/007-architecture.md:391`), and it polls the management API (`src/client/provider.tsx:74`) rather than streaming a conversation. A real chat entry should use DSH's chat components/theme rather than extend this admin UI.

## Feasibility-relevant findings (10 lines)

1. This is not a chat product: it is a GitHub/Feishu-triggered, policy-gated work engine whose DSH UI is a supervision panel, not a conversation.
2. The sidebar entry already exists and opens the management panel; the panel already has an "Open main Session" button that opens the superagent's DSH chat Session (`src/client/app.tsx:134-135`).
3. Chat UI itself belongs to DSH; this bundle ships none and declares no dependency on DSH's chat client packages, so a chat page/sidebar-to-chat binding must be added or reuse DSH's session view.
4. Turning chat text into real work is the hard gap: authorization requires a Source Trigger/identity/allowed list, and no DSH-chat Source, API route or tool exists (`src/app/api.ts:21-45`; `docs/002-authorization.md:9-17`).
5. The main Session is an event-driven router with a complete custom prompt, no ask/present tools, and instructions never to investigate or wait (`src/app/sessions.ts:244-264`; `prompts/orchestrator.md:16`).
6. A chat session must bind to the plugin-managed `masterId` Session, created only after GitHub/stateDir/model setup succeeds (`src/app/runtime.ts:104-105,201-211`); before setup there is no chat to open.
7. Setup is heavyweight: dedicated agent GitHub account + isolated `gh` wrapper + repo + clone/prepare command + model provider; optional Feishu bot + `lark-cli` (`docs/006-deployment.md:21-69`).
8. Version risk is real: the repo targets DSH 0.2.1 (build clean there), the packaged Desktop app bundles 0.2.2-rc.1, a probe shows 8 typecheck/API-drift errors against 0.2.2, and semver does not match `^0.2.1-alpha.2` with `0.2.2-rc.1`.
9. Install-path risk: repo docs use a dedicated `superagent` profile/port/tmux service and manual profile patch, while this Desktop environment expects `plugin_manager install_bundle`; the required `stateDir` must be provided before the plugin can mount.
10. Reusable assets are substantial and MIT-licensed (domain engine, policy/gate, Source protocol + cookbook, prompt suite, DSH session/executor glue, panel/locales), so a "superagent chat" plugin is best built by reusing this core and adding a DSH-chat Source + chat surface rather than wrapping the repo as-is.
